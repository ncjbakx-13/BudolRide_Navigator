# Delivery Plan

This plan prioritizes a demonstrable, reliable route-planning flow over feature breadth. Each stage must meet its acceptance checks before the next stage adds complexity.

## Stage 0: Foundation

Owner: Aaron and Nathaniel

- Resolve D-001 through D-007 in `docs/DECISIONS.md` where needed for the next stage.
- Rotate the exposed database credential and configure local `.env` files from the committed examples.
- Use Python 3.12 as the minimum supported runtime. When code changes resume, reconcile `backend/pyproject.toml`, lockfiles, and setup instructions with that decision.
- Choose the package workflow, formatter, linter, and test commands.
- Remove generated bytecode from version control in a separate reviewed cleanup if it is tracked.

Acceptance: a new contributor can follow documented setup without receiving a secret, and local checks are named and reproducible.

## Stage 1: Trusted spatial data

Owner: Nathaniel

- Define the migration-backed POI schema with source-element identity, provenance, timestamps, categories, and spatial indexes.
- Convert the initial OSM script into a configurable, idempotent ETL command with fixture tests and run metrics.
- Prepare a bounded Cavite OSRM dataset and a small suite of known cycling routes to validate the bicycle profile.

Acceptance: repeated ingestion does not create duplicates, every published POI has provenance, and prohibited-road regression cases have documented expected results.

## Stage 2: Read-only route API

Owner: Aaron, with routing inputs from Nathaniel

- Add FastAPI settings, database connection lifecycle, health/readiness endpoints, structured error responses, and request IDs.
- Implement a typed, authenticated route-preview endpoint backed by OSRM. Enforce Supabase JWT validation, Cavite boundary, coordinate validation, timeout budgets, and response-size limits.
- Add API and spatial database tests using controlled fixtures.

Acceptance: the endpoint returns a validated base route or a documented error without exposing internal details.

## Stage 3: Mobile route preview

Owner: Aaron

- Replace the Expo starter view with a route-planning screen, origin/destination input, loading/error/empty states, and route geometry rendering.
- Configure the chosen map provider without committing platform keys.
- Add a device smoke test and accessibility checks for the planning flow.

Acceptance: a rider can preview a known Cavite route on a physical device or emulator with understandable failure states.

## Stage 4: POI detours and elevation

Owner: Aaron and Nathaniel

- Implement bounded PostGIS corridor queries and deterministic candidate scoring for one optional POI.
- Re-route through the selected waypoint and return why it was selected.
- Add cached elevation profiles, an elevation chart, and the documented steep-climb summary.

Acceptance: the 0.5 km to 5 km detour control is enforced end to end, no candidate query is unbounded, and missing enrichment degrades cleanly.

## Stage 5: Authentication and release hardening

Owner: Aaron

- Implement the confirmed authentication decision, JWT validation, ownership checks, rate limits, production CORS, and secure token storage.
- Add source attribution, privacy text, operational monitoring, deployment configuration, and CI quality gates.
- Perform a release security review against `docs/SECURITY.md`.

Acceptance: protected features are authorized end to end, secrets are absent from source/history-facing artifacts, and a deployment has a documented rollback path.
